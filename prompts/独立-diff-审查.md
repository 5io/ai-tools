# 独立 diff 审查

在同一仓库另开一个审查会话，把下面的提示词贴进去。工作区有未提交变更时，选中能看到这些变更的 checkout 或 worktree，并明确要审 staged、unstaged 或两者，以及是否包含未跟踪文件。

~~~text
请独立审查这次改动。仅做只读审查，不修改文件、不提交、不合并。

已批准的方案或验收条件：【完整提交 SHA 加仓库相对路径 / 独立提供的可信快照或验收条件】
已批准的改动范围：【范围 JSON 的完整提交 SHA 加仓库相对路径 / 独立提供的可信快照 / 已批准方案中的范围；未知请标明】
基线：【提交 SHA / 分支或 PR 的 base】
待审版本：【提交 SHA / PR / 当前工作区 staged、unstaged 或两者，以及是否包含未跟踪文件】

先核实获批来源、基线和待审版本。按批准版本读取方案、范围及涉及授权的项目约定。把候选改动对这些资料的变更单独列出，等待确认后才按新范围判断。走查代码前，列出实际变更，对照允许范围，标记范围外、禁改或高风险文件，以及缺少 diff 或测试证据的验收项。把核对结果放在结论之后、详细发现之前。可以阅读相关调用方和测试来证实结论。若来源或覆盖范围不完整，继续审查已经明确的部分，并指出哪些结论受限。

1. 若安装了 5io-code-review 且可执行 Git 和 Node.js，先运行随 Skill 提供的范围检查。仓库内获批文件使用 --scope-ref 完整提交 SHA 和 --scope 仓库相对路径。若工具报告工作树检查不完整，标明未检查的部分，可改审提交或暂存区快照。核实范围异常是否有已确认的例外，并说明对交付的影响。
2. 跟踪关键用户路径，检查正常操作、失败路径和回归。根据改动判断是否涉及数据兼容性、权限、并发或恢复。
3. 检查是否复用仓库已有能力，是否引入会影响维护或运行的重复实现、冗余逻辑或性能问题。
4. 按方案里的验收编号核查测试是否能抓住相应回归。把代码阅读所得、已有测试证据和仍需复跑的场景讲清楚。

先给结论，再按「阻塞」「建议」列发现。每条给出文件和行号、触发条件、实际影响和修正方向。把需要产品决定的取舍单独列出。最后写明审查了哪个范围、还有什么未验证。如果未发现阻塞项，直接写明，不凑问题。
~~~
