# 独立 diff 审查

只读工作树和必要的项目资料。确认基线、待审版本和实际范围。对工作区改动区分 staged、unstaged 和未跟踪文件。范围不全时报告缺口，并审查已明确的部分。

1. 先核查范围漂移、禁改路径和遗漏的验收条件。
2. 跟读关键路径及调用方。按改动核对正常场景、失败和恢复，以及相关兼容性、权限和并发问题。
3. 检查重复实现和实际运行成本。检查相关测试是否能捕捉这次改动会引入的回归。
4. 给出结论和发现。每条写文件与行号、触发条件、影响及修正方向，分为阻塞和建议。标明实际检查过的范围、已有证据和仍需复跑的场景。

发现需要产品决定的取舍时单列。只报告有证据的问题。

## 锁定审查对象

- 已提交改动或 PR：确认基线语义。PR 通常查看从分叉点到待审提交的变化，明确指定两个快照时按快照比较。
- 未提交改动：分别核对暂存区和工作区。整体验收要看组合后的最终内容。未跟踪文件按约定单列，避免误当成已有 diff 的一部分。
- 缺少确认版方案时，使用用户提供的验收标准和仓库既有行为，标明哪些范围或取舍无法核对。

## 按风险走查

- 局部改动：检查入口、默认状态、直接调用方和能发现回归的测试。
- 核心逻辑：跟到状态或数据边界，检查空输入、中途失败、重试、重复执行和恢复。按变化选择迁移、权限、并发或旧调用方兼容性。
- 打包或配置：核对实际构建产物、运行入口与环境参数。仅看到源码测试时，把部署或运行时行为标为待验证。

判断测试质量时，从可预期的回归倒推。比如需求明确包含零值记录，仅用正值样例即使通过也无法覆盖漏计。只有能说明为什么会发生、有谁受影响、如何验证的问题才列为发现。

## 回报

先写可否按当前证据进入合并检查，再列「阻塞」和「建议」。发现包含引入问题的行、触发条件、用户或系统影响、修正方向和支持证据。只读审查期间需要会写文件的验证时，列出建议复跑步骤和原因。
