# 人话方案

先只读核对实际入口、可复用实现和验证命令。范围与验收明确的小改动可直接按用户授权进行。对有取舍的任务先对齐，再落地。跨模块里程碑可把确认版存入仓库，便于后续聊天按同一版本接手。

方案用产品和工程都能读懂的语言写清：

1. 用户怎么用。写入口、默认行为、反馈和失败后的恢复路径。
2. 大概怎么做。写改动模块、复用点、影响范围和范围外事项，附关键文件路径。
3. 有哪些取舍。只把会改变用户体验、数据兼容性或交付范围的问题交给用户，附建议和理由。
4. 怎么验收。写前置条件、操作、预期结果和已核实的测试命令。

用户要求先规划时，在确认前保持只读。必要时邀请有独立上下文的审查者用真实文件核对方案，按宿主能力与授权执行。

## 选择方案深度

- **小改**。单一行为、改法和验收都明确时，写明改动与快测即可。
- **需对齐**。用户可见行为、接口或兼容性有可选决策时，先给推荐做法与实际取舍。只追问会改变交付的决定。
- **跨模块**。需要分期交付、迁移或多个会话接手时，写出可独立验收的里程碑、依赖顺序和每段的负责人或待分配范围。涉及状态迁移时写明旧数据、新旧版本交叠及恢复路径。

确认方案后，交接时附获批方案和范围的完整提交 SHA 加仓库相对路径，或独立提供可信快照。同时给出 Git 基线、已决定的行为与验收步骤。发现新证据推翻原决定时，说明受影响的验收场景和建议调整，等新版本范围获批后继续。

跨会话交付时，为关键验收场景编号，例如 AC-1。把快测和合并检查分别写明命令及工作目录。需要确定性范围检查时，随方案保存范围文件，字段为 `allowed`、`restricted`、`highRisk`。每项是仓库相对文件路径或以 `/` 结尾的目录路径。方案正文引用范围文件，范围未知时如实标注。

## 什么算可验收

例如「支持批量重试」需要说明部分成功时失败项是否保留选中，以及重复点击是否会发起第二次请求。验收应能写成「选中三项，其中一项失败；成功项退出列表，失败项保留并显示可重试状态」。一次确立默认行为，后面的实现和审查使用同一条验收标准。
